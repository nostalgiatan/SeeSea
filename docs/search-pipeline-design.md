# 元搜索与检索管线设计

状态：草案，待评审。未涉及任何代码改动。

## 1. 定位

核心竞争力是**通用高质量搜索**：召回广、排序准、来源可追溯，并且每条结果自带可用正文。中文不是差异化点。

差异来自三件事叠加：

1. **融合**：多个独立来源的结果合并，多源同时命中本身是质量信号。
2. **内容感知的精排**：抽取只要约 7 ms/页（见 `extraction-design.md`），所以可以对前 k 条抓正文，用真实内容重排，而不只看摘要。
3. **闭环**：排序特征、站点先验、评测集随使用积累，模型可定期重训并热替换。

## 2. 来源策略

- **主力**：官方 API（如 Brave 等，可得性与条款需逐个核实）和自部署 SearXNG 的 JSON 接口。
- **补充**：抓取型引擎只保留少数最稳定的（候选：Bing 网页/新闻、百度网页、搜狗网页）。其余（360、Yandex、Bilibili、Unsplash、图片/视频类、微信）移除，或放入可选插件 crate。保留名单以健康数据和固定样本测试结果为准。
- **垂类**：新闻、代码、学术、行情、RSS，按意图路由，不参与通用扇出。

每个来源声明能力：语言、时间范围、分页、类别、速率上限、是否需要密钥。

## 3. 管线总览

```
请求 + 预算
  → 1 查询理解
  → 2 扇出
  → 3 规范化与去重
  → 4 一级排序（摘要级）
  → 5 抓取 top-k
  → 6 抽取
  → 7 二级精排（正文级）
  → 8 段落/章节选择
  → 9 输出组装
  → 10 反馈与学习（旁路）
```

三种模式共用同一条管线，区别只是启用多少级：

| 模式 | 来源数 | 抓取 | 精排 | 章节选择 |
|---|---|---|---|---|
| fast | 2–3 | 否 | 仅一级 | 否 |
| standard | 全部适用来源 | top-k 小 | 一级 + 二级 | 向量/交叉编码器 |
| deep | 全部 + 查询改写 | top-k 大 | 一级 + 二级 | 加 LLM 树推理（可选） |

**降级原则**：每一级都可缺席。重排模型不可用就用一级顺序；抓取失败就保留摘要；任何一级都不能让整个请求失败。

### 3.1 查询理解
- 规范化、语言识别、意图分类（通用/新闻/代码/学术/金融）、时效需求判断。
- 路由：决定扇出到哪些来源。
- 改写与拆分复杂问题：仅 deep 模式，先规则，LLM 为可选。

### 3.2 扇出
- 并发请求，带超时、对冲请求（慢来源不拖整体）、熔断、限流。
- 查询缓存，TTL 按意图区分（新闻短，参考类长）；同一查询的在途请求合并。
- 来源健康度持续记录，供路由和权重使用。

### 3.3 规范化与去重
- URL 规范化：去跟踪参数、AMP/移动版归一、协议与尾斜杠归一。
- 近重复：标题+摘要的 simhash；抓取正文后再按正文去重。
- 保留溯源：每条结果记录被哪些来源、以什么名次返回。

### 3.4 一级排序（摘要级，便宜）
加权 RRF 作基线，之后换成 GBDT（复用现有 forust 栈）。特征：
- 各来源名次、多源命中数、来源健康权重
- 域名先验、新鲜度
- 查询与摘要的词项重合
- 标题特征（**折扣后**使用，见 §4）

### 3.5 抓取
- 只抓一级排序的 top-k，有总预算和并发上限，遵守礼貌抓取。
- 条件请求与页面缓存。
- 抽取结果 `needs_render` 为真时，交给渲染层（Lightpanda）重试。

### 3.6 抽取
- 直接使用 `seesea-extract`：`core`、`sections`、`meta`、`confidence`、`needs_render`。
- 抽取失败或置信度低的页面降权，而不是丢弃。

### 3.7 二级精排（正文级）
- 交叉编码器：查询 × 最相关段落。
- 嵌入相似度：用于语义去重与段落打分。
- 正文质量：抽取置信度、有效字数、模板占比。
- 发布时间：来自 `meta.published`，与时效需求匹配。
- **标题-正文一致性**（§4）。
- 候选集小（几十条），向量现算，不需要持久化向量库。

### 3.8 段落/章节选择
- 抽取结果按标题层级得到文档树（免费，不需要 LLM 建树）。
- 对每个节点用向量/交叉编码器打分，只返回相关节点，受 token 预算约束。
- deep 模式可选：参考 PageIndex 的做法，让 LLM 沿树推理选择章节。它对长文档内部检索有效，但每次查询都调用 LLM，不适合做全网排序的第一层。其基准数据为厂商自测，尚未独立验证。

### 3.9 输出组装
每条结果包含：URL、标题、命中的来源与名次、各级得分明细、置信度、发布时间、是否已抽取正文，以及 Core 与 sections（在预算内）。得分明细保留，方便调试和 Agent 自己判断可信度。

### 3.10 反馈与学习（旁路）
- 记录请求、结果、Agent 的使用信号（被引用、被丢弃）、人工标注。
- 定期用缓存特征重训一级与二级排序模型，热替换。
- 评测回归门：新模型必须在评测集上不低于旧模型才能上线。

## 4. 标题权重原则

标题没有独立权重。标题只有被正文验证之后才有意义，否则标题党会直接污染排序。

**有效标题得分 = 查询-标题匹配度 × 正文对标题的支撑度**

- **支撑度**由标题-正文一致性给出：标题中的实体、数字、关键断言在正文里有没有出现；标题与正文开头段落的语义相似度；`<title>`、`og:title`、`h1` 三者是否一致。
- **标题党特征**：夸张词、疑问式吊胃口、标题里的实体在正文中缺失、标题长度异常、域名上的标题党先验。
- 标题匹配高但正文不支撑时，标题项贡献趋近于零，甚至为负。

**权重随信息逐步获得**：

| 阶段 | 可用信息 | 标题权重 |
|---|---|---|
| 一级（只有摘要） | 标题、摘要、域名先验 | 折扣使用，用摘要-标题一致性与域名先验估计支撑度 |
| 二级（已抽取正文） | 完整正文 | 用正文支撑度替换估计值，权重按验证结果取值 |

这两项都作为 GBDT 特征由数据学习，而不是写死系数。

**验证方式**：评测集里专门构造对抗样本，即标题与查询高度匹配但正文无关或空洞的页面，要求它们排在正文相关的页面之后。这一项单独报告。

## 5. 接口（Rust trait 草案）

- `SearchSource`：声明能力，`search(query, params) -> Vec<RawResult>`
- `Fetcher`：`fetch(url, opts) -> Page`，含缓存与渲染降级
- `Extractor`：即 `seesea-extract`
- `Ranker`：一级与二级共用，`score(features) -> f32`，可热替换
- `Reranker`：交叉编码器接口，实现可替换
- `Store`：见 §6

每个 trait 都应该能被换掉，换掉的代价只是一个 crate。

## 6. 存储

- 存储内容：搜索缓存、页面缓存、抽取结果、站点模板、反馈与评测数据。均为嵌入式本地状态。
- 定义 `Store` trait，先以 Turso 实现。Turso 为 MIT 协议、纯 Rust，支持并发写（MVCC）、变更捕获、原生向量类型。
- 风险：尚未到 1.0，SQLite 兼容性不是 100%，全文检索、加密、多进程 WAL 标为实验性，近似向量索引尚未实现，官方建议保留独立备份。
- 因此：不把 Turso 放在关键路径的唯一依赖上；保留换成 libSQL 或 rusqlite 的退路；向量暂不依赖其向量能力；全文检索不依赖其实验性 FTS。

## 7. 评测

没有评测集就无法设计排序，先于实现建立：

- 查询集：覆盖通用、新闻、代码、学术、金融、时效性强的问题、长尾问题。
- 标注：相关性分级，LLM 辅助加人工抽检。
- 指标：nDCG@10、召回；下游指标为同一问题用不同搜索结果喂给 LLM 后的回答正确率。
- 对照：在同一批查询上对比其他搜索 API 的结果。
- 专项：标题对抗集（§4）、重复与镜像站点、时效性。

注意：当前沙箱无法访问大多数搜索引擎，真实召回与排序评测需要在可联网的机器上运行，查询结果落盘后可复现。

## 8. 分阶段

1. 接入 `seesea-extract`，替换 `seesea-cleaner` 的抽取路径，保留开关对比新旧。
2. 精简抓取型引擎，补固定样本解析测试，增加 SearXNG 与官方 API 来源。
3. 建立搜索评测集与评测框架。
4. 一级排序（RRF → GBDT）与标题折扣特征。
5. 抓取、抽取串入管线，二级精排与标题-正文一致性。
6. 章节选择；deep 模式的树推理。
7. 存储 trait 与 Turso 实现；反馈回流与重训。
