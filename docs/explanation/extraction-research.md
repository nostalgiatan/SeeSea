# 正文提取（`seesea-extract`）调研与设计草案

这是正文抽取模块设计阶段的研究记录，保留了当时的调研、基准数据和决策过程。`seesea-extract` 已按其中的结论实现；文中的数字是当时测得的，之后的代码可能已不同。

状态（写作时）：草案，供讨论。所有外部数字都来自论文或作者自述，未经我们复现，复现是第一步（见"落地顺序"）。

## 1. 为什么这个模块是重点

`/search` 的片段、`/extract` 的正文、`/crawl` 的页面内容，最终都经过它。它的输出质量直接决定产品质量；
抓取、调度、缓存都是工程问题，这里才是算法问题。

## 2. 对 firecrawl/html-extractor 的诊断

读了源码（3.2k 行，`crates/html-extractor/src`）并用最小样例复现：

```html
<p>A <strong>closure</strong> is ... the <a href="/x">lexical environment</a> around it.</p>
```
输出：`A is ... the around it.**closure**[lexical environment](/x)`

**根因是数据模型，不是渲染 bug。** `parser.rs` 把一个元素下所有文本节点拼成一个 `own_text` 字符串，
渲染时先输出 `own_text`，再输出子元素，文本与子元素的交错顺序在解析时就丢了。
任何带行内元素（链接、粗体、`<code>`）的段落都会错序。要修就要改 `tree.rs`、`parser.rs`、`render.rs`，
约占全库三分之一，实际上是重写。

**它为什么没被测试发现：** 常见的提取评测（含下面的 WCXB）用的是词袋 F1，对顺序不敏感。
我们的评测必须加顺序敏感的指标，否则同样的问题会再次溜过去。

其他观察（来自我们的 16 页测试，样本小）：
- 首页和列表页表现差（新浪首页选中了页脚）。
- 商品页和 SPA 页提取量过少。
- 质量分作为"是否升级到渲染"的信号是有用的。
- 打分权重是手工调的，调参对象是约 55 个自带样例，没有公开基准成绩。

## 3. 现有方案与基准

基准：**WCXB**（2026 年论文，2,008 页、7 种页面类型、CC-BY-4.0，含 HTML 与标注），
指标是词袋 F1。开发集（1,497 页）成绩：

| 类型 | rs-trafilatura | MinerU-HTML | Resiliparse | Trafilatura | ReaderLM-v2 |
|---|---|---|---|---|---|
| 文章 | 0.932 | 0.928 | 0.871 | 0.924 | 0.880 |
| 文档 | 0.931 | 0.838 | 0.883 | 0.888 | 0.776 |
| 服务页 | 0.843 | 0.824 | 0.815 | 0.751 | 0.708 |
| 论坛 | 0.792 | 0.794 | 0.758 | 0.575 | 0.589 |
| 集合页 | 0.713 | 0.506 | 0.586 | 0.518 | 0.415 |
| 列表页 | 0.704 | 0.710 | 0.620 | 0.550 | 0.578 |
| 商品页 | 0.670 | 0.619 | 0.608 | 0.562 | 0.464 |
| 总体 | 0.859 | 0.827 | 0.797 | 0.791 | 0.741 |

要点：
1. **文章页已经基本解决**（各家都在 0.87 以上），差距全在非文章页（相差 14 到 30 个点）。
   所以"通用打分选一个最大子树"这条路本身有天花板，核心问题是页面类型。
2. rs-trafilatura 是 Rust 实现，MIT/Apache，思路是 XGBoost 分类页面类型，再按类型套规则，并带置信度。
   **注意：它的作者同时是 WCXB 的作者，并在开发集上调参，所以应看保留的测试集（0.903 对 0.841）。**
3. 神经方案（MinerU-HTML/Dripper，0.6B 模型做块级二分类；ReaderLM-v2，1.5B 生成式）没有超过最好的启发式，
   且慢得多（论文称 1.6 到 10 秒/页，用 A100）。ReaderLM-v2 是 CC BY-NC，不能商用。MinerU-HTML 的代码和模型许可证我没核实。
4. 论文给出的失败模式：论坛里评论类 class 被当噪声删掉；集合页的筛选栏混入；商品内容在 JSON-LD 里而 DOM 提取看不到；
   服务页内容分散在多个 section；列表页只抓到一张卡片。

## 4. 设计

### 4.1 总体管线

```
bytes + url + headers
  → ① 解码           编码探测（meta、BOM、统计探测；GBK/GB18030/Big5 必须正确）
  → ② 解析           html5ever → 自有 arena DOM，子节点序列包含文本节点（修掉上面的根因）
  → ③ 结构化数据     JSON-LD、OpenGraph、microdata、内嵌状态（__NEXT_DATA__ 等）
  → ④ 页面分类       URL 特征 + DOM 特征 + schema.org 类型 → 7 类 + 置信度
  → ⑤ 分块           DOM 切成有序"块"序列，每块带特征
  → ⑥ 块打标         可解释打分 → 以后换成离线训练的小模型；序列平滑
  → ⑦ 按类型选取     文章：连续主区域；论坛/列表：重复单元；商品：结构化数据加主区域
  → ⑧ 渲染           保持顺序的 Markdown；链接、表格、代码、图片
  → ⑨ 质量与升级信号  置信度 + 是否像 JS 空壳
```

### 4.2 关键决策

**① 解码。** 中文站大量 GBK。先解码再解析，别让上层传 `&str`。输入类型用 `&[u8]` 加响应头。

**② 数据模型。** 节点的子序列是 `Vec<Child>`，`Child` 是 `Text | Element`。这是对 html-extractor 的根本修正。
渲染按文档顺序走一遍，行内元素就地输出。

**③ 结构化数据先于 DOM。**
- JSON-LD 的 `Product`、`Article`、`NewsArticle`、`QAPage`、`DiscussionForumPosting`，直接给出商品或文章字段。
- 内嵌状态（`__NEXT_DATA__`、`__NUXT__`、`window.__INITIAL_STATE__`）能解决相当一部分"SPA 空壳"，
  不需要启动浏览器。这一步便宜，应当先于渲染升级。

**④ 页面分类。** 先用规则（URL 路径、`og:type`、schema.org 类型、重复结构比例），数据够了再换离线训练的梯度提升树。
推理用我们自己的几十行树遍历代码，不引入运行时 ML 依赖。输出置信度；低置信时保守地走通用文章路径。

**⑤⑥ 分块与打标。**
- 块 = 叶子级块元素（`p`、`li`、`h*`、`pre`、`td` 等）加其祖先路径。每块特征：文本长度（按字符，不按词）、链接密度、
  标点密度、标签路径、class/id 词元、文档位置、深度、兄弟结构相似度。
- 中文无空格分词，也没有英文停用词，特征要用字符数与句末标点（。！？；）密度，不能照搬英文启发式。
- 打标先用可解释的加权和，再叠一层序列平滑（相邻块倾向同一标签，类似 boilerplate 去除研究里的两状态序列模型）。
- **块序列就是将来接神经分类器的接口**：Dripper 的做法也是给块二分类。我们保持这个接口，
  低置信页面以后可以交给小模型复判，而不必改管线。

**⑦ 按类型选取。** 这里是拉开差距的地方，对应第 3 节的失败模式：
- 文章/文档：连续主区域加标题、日期、作者；代码块必须完整保留。
- 论坛：检测重复的"帖子单元"（兄弟节点结构相似），保留全部单元，不能按 class 名含 `comment` 就删。
- 列表/集合：同样用重复单元检测，输出为列表，过滤筛选栏与分页。
- 商品：JSON-LD 字段为主，DOM 区域补充描述。
- 服务页：允许多个 section，按文档顺序合并。

**⑧ 渲染。** 单遍、按文档顺序、行内就地输出；相对链接按 base URL 解析；表格转 GFM；图片保留 alt。
输出同时给 Markdown 和"块列表"（含各块来源位置），后者供分块向量化与引用溯源使用。

**⑨ 升级信号。** 输出 `confidence` 和 `needs_render`（脚本占比高、可见文字极少、存在框架挂载点、`<noscript>` 提示等）。
调度层据此决定要不要送去 Lightpanda 渲染。

### 4.3 明确不做（第一阶段）

- 不做生成式 LLM 提取。慢、贵，评测上也没赢过启发式。
- 不做站点专用规则库（维护成本无底洞），除非数据显示某几个高频站点值得。
- 不用 ReaderLM-v2（许可证不允许商用）。

### 4.4 结合两者：候选融合加块级监督分类器（基于 5.3 的数据提出）

动机：两者的错误高度互补。若每页都能挑中更好的那个（页面级上限，不可达），WebMainBench 上可到 0.84 至 0.85（对比单个的 0.76 至 0.79），
WCXB 上到 0.88（开发集）和 0.92（测试集）。同时约 10% 的页面两者都低于 0.5，这部分选谁都没用，需要新的信号。

做法：
1. 一次解析、共享 DOM，把 html-extractor 的打分和 rs-trafilatura 的选取当作**特征生成器**，不再把它们当最终答案。
2. 把 DOM 切成块，每块的特征包括：两个提取器各自是否选中、链接密度、文本长度、标点密度、标签路径、class/id 词元、位置、页面类型等。
3. 用**监督分类器**给每块打标（小型梯度提升树，CPU 毫秒级），再做序列平滑。
4. 训练数据：WebMainBench 的 7,809 页，`html` 字段里有人工标注的 `cc-select="true"` 标记
   （抽查前 400 页，每页都有；只标了正例，未标即负例），覆盖 46 种语言。这是块级监督，不是页面级。
5. 评测：WCXB 与 WebMainBench 分别留出测试集，按页面类型和语言分组出表；不要用训练集上的成绩。

预期与风险：
- 页面级上限是 +0.07 至 +0.08，块级监督有机会超过它，但**这只是假设，没有验证**。
- 神经方案（Dripper 0.6B）在 WebMainBench-545 上报告 ROUGE-N 0.88 至 0.89，我们是 CPU 小模型，不可能无条件追平，目标是在 1/10 的延迟下拿到大部分收益。
- 标注只有正例标记，要确认"未标记"是否都是真负例（例如标注者漏标）。需要先抽样人工检查。
- 训练集里的网页内容版权归原站，分类器只学习结构特征而非文本，风险较低，但仍需你确认是否接受。
- 评测集与训练集必须按域名切分，防止同站泄漏。

### 4.5 输出契约：核心加带标签的区块（已决定）

决定：输出不是一段文字，而是分层结果，由调用方取舍。

```
ExtractResult {
  core:      { title, markdown, blocks[] }        // 标题加正文核心，口径同基准参考答案
  sections:  [ { kind, markdown, confidence } ]   // 非核心但可能有用的区块
  discarded: { nav, footer, ads, cookie, ... }    // 只记录数量与类型，不返回正文
  meta:      { author, date, language, canonical_url, schema_org, ... }
  page_type, confidence, needs_render, diagnostics
}
```

- `sections.kind` 初定：`specs`（规格、参数）、`comments`、`related`、`table`、`list`、`faq`、`author_bio`、`shipping_policy`。
- `core.blocks[]` 保留每块在原 DOM 中的位置，供分块向量化与引用溯源。
- **评测分两部分：**
  - 核心用现有基准（精确率、召回、F1），口径一致；`sections` 不应计入核心的精确率。
  - `sections` 的分类与边界，基准测不到，需要我们自己的小评测集（约 300 页，LLM 起草加人工抽检，先定类型表），在第一版核心稳定后再建。

## 5.5 两项补充检查

**1. 基准里人工标注的块标记可以当监督数据。** 对 WebMainBench 前 1,500 页检查（`extract-eval audit-labels`）：
- 标记区域的文本与参考答案的词袋 F1 平均 0.993（中位数 1.000，20 页低于 0.9）。
- 41.9 万个含文本的块里，37% 是正例；**没有一个块是半标半不标的**（混合块 0 个），块级标签是干净的。
- 前提仍是"未标记即负例"；漏标无法用这个方法发现，需要抽样人工检查。

**2. 一个本该最先做的基线：什么都不提取，直接输出整页可见文本。**

| 提取器 | WebMainBench 全量（7,809 页） | WCXB 开发集（1,497 页） |
|---|---|---|
| 整页文本（不提取） | 0.668 | 0.689 |
| html-extractor | 0.762 | 0.781 |
| rs-trafilatura-text | 0.771 | 0.847 |

读法：
- **现有提取器在 WebMainBench 上只比"不提取"高 0.09 至 0.10。** 之前看到的 0.76 至 0.79 没有那么好，提升空间主要在精确率。
- **WCXB 的论坛页上 html-extractor（0.399）比不提取（0.472）还差**；集合页和列表页只略好一点。这类页面它基本是在帮倒忙。
- 评测报告里必须永远带上这条基线，任何新方案先要超过它才有意义。

## 5. 评测先行

1. **主基准：WCXB 开发集和测试集**（CC-BY-4.0，可直接用）。按页面类型分别报告，不只看总分。
2. **补一个中文集：** 新闻、博客、论坛、商品、政务、文档各 30 到 50 页，共 200 到 300 页。
   标注可由 LLM 起草再人工抽检，我们自己定一个抽检比例并记录，不要重复 WCXB 不报告一致性的问题。
3. **指标：** 词袋 F1（与论文可比）加**顺序敏感指标**（最长公共子序列比、归一化编辑距离）、
   **链接保留率**、**行内格式保留率**。第 2 节的错序问题只有后者能抓到。
4. **基线同台：** 当前 html-extractor、rs-trafilatura、Python trafilatura、Resiliparse。
5. **回归门禁：** CI 对固定样例集跑分，按类型设下限，低于下限则失败。

顺序类指标（只有开发集带 Markdown 标注）

| 指标 | html-extractor | rs-trafilatura-md | 上限（oracle） |
|---|---|---|---|
| 词袋 F1 | 0.781 | 0.841 | 0.999 |
| 顺序敏感 F1（LCS） | 0.746 | 0.829 | 0.999 |
| 行内跨度保序率（粗体与链接保持相邻词） | 0.228 | 0.773 | 0.976 |
| 同上，只算词本身出现了的跨度 | 0.266 | 0.826 | 0.977 |

读法：
- html-extractor 的词袋 F1 与 LCS F1 只差 3.5 个点，所以**词袋指标几乎看不出行内错序**；保序率却只有 0.23，行内错位非常普遍。
- rs-trafilatura 的保序率为 0.77，明显好，但离上限 0.98 仍有距离。论坛、集合、列表、商品页上只有 0.47 至 0.56，这是我们自己能做得更好的地方。

rs-trafilatura 的两个 Markdown 与文本版本差别很小，说明 Markdown 渲染不是它的瓶颈。

局限：WCXB 主要是英文，rs-trafilatura 的作者同时是 WCXB 的作者，这里的数字不能代表中文页面。

## 5.2 多语言基线（WebMainBench 的 545 页人工校正子集）

数据来自 opendatalab/WebMainBench（Apache-2.0；网页内容版权归原站，只用于评测，不入库）。参考答案是人工校正的 Markdown，
含代码、公式、表格，与 WCXB 的标注方式不同。词袋 F1（CJK 按字符切分）：

| 分组 | 页数 | html-extractor | rs-trafilatura-text | rs-trafilatura-md |
|---|---|---|---|---|
| 全部 | 545 | 0.817 | **0.827** | 0.816 |
| 拉丁文字 | 465 | 0.817 | 0.827 | 0.817 |
| 中文（按文字判定） | 70 | 0.821 | **0.848** | 0.821 |
| 难度：简单 | 163 | 0.907 | 0.892 | 0.882 |
| 难度：中等 | 218 | 0.847 | 0.832 | 0.827 |
| 难度：困难 | 164 | 0.686 | **0.757** | 0.736 |

要点：
- **两者在这个数据集上几乎持平**（0.817 对 0.827），与 WCXB 上的明显差距（0.781 对 0.847）不一致。
  所以"rs-trafilatura 明显更好"这个结论依赖数据集，不能当作定论。rs-trafilatura 的优势集中在困难页面。
- **绝对分数只有 0.82 到 0.85**，说明两者离上限都还有约 15 个点的空间。
- **中文只有 70 页**，两者相差 0.027，落在统计误差内，不能据此下结论。其他语言（日 4、阿拉伯 2、韩 2、俄 1）样本太少，无法评价。
- 该子集的元数据有缺：94 页没有语言标注，其中 42 页主要是中文，另有 3 页标成英文实为中文。因此框架另外按文字自动判定语言（`--group-by script`）。
- 参考答案里几乎没有行内粗体和链接（只有 22 页有），所以**行内保序指标在这个数据集上没有意义**，已忽略。
- 全量 7,809 页（含 716 页中文和 46 种语言）还没拿到，需要它才能评价中文和其他语言。

## 5.3 全量 WebMainBench（7,809 页，1.35GB）

参考答案是标注区域经 html2text 转出的 Markdown；语言元数据只有 `en`/`non_en`，所以按文字判定分组。词袋 F1：

| 分组 | 页数 | html-extractor | rs-trafilatura-text | 配对差（rs 减 html，95% 置信区间） |
|---|---|---|---|---|
| 拉丁文字 | 6,973 | 0.758 | 0.771 | +0.013 [+0.005, +0.020] |
| 非拉丁文字 | 836 | 0.788 | 0.772 | −0.017 [−0.034, +0.001] |
| 其中中文 | 697 | 0.793 | 0.776 | （未单独算） |
| 其中俄/日/阿/韩 | 46/45/20/19 | 0.705/0.812/0.811/0.748 | 0.713/0.751/0.906/0.681 | 样本太小 |

非拉丁文字里，rs-trafilatura 的 Markdown 输出（0.732）明显低于文本输出（0.772）。

结论（比之前的更可靠，因为样本量大）：
1. **在这个大型、多语言、人工标注的基准上，两者基本等价，都只有 0.76 到 0.79。** 差距在 ±0.02 以内，中文上 html-extractor 甚至略好。
2. WCXB 上 0.781 对 0.847 的差距，主要来自它的页面类型（论坛、商品、集合等）。WebMainBench 没有这些类型标签，所以这类页面在这里被稀释了。
3. **两者的共同问题：** 都有约 150 个非拉丁页面 F1 低于 0.5（共 836 页），平均精确率约 0.75，召回约 0.89。也就是说都倾向于多取，混入了不该有的内容。
4. 因此"用 rs-trafilatura 当基础"不再是显然的选择。真正的结论是：**没有现成方案足够好，提升空间约 20 个点**，值得自己做；基础是哪个并不关键。

## 5.4 失败分析：两个提取器都低于 0.5 的页面

范围：WebMainBench 中两者词袋 F1 都低于 0.5 的页面（非拉丁文字 82 页，拉丁文字 719 页，约占 10%），WCXB 开发集 97 页（6.5%）。
先按精确率与召回率自动分类，再抽样 36 页（中文 18、拉丁 18）人工对照参考答案阅读。分类依据是统计量，原因判断来自抽样，样本小，只能作为方向。

### 自动分类（两者都失败的页面中）

| 类型 | 判据 | WebMainBench 拉丁 | WebMainBench 非拉丁 | WCXB 开发集 |
|---|---|---|---|---|
| 多取 | 精确率 < 0.3，召回 ≥ 0.6 | 约 35%（246 / 285） | 约 45% 至 60%（37 / 51） | 约 27% 至 35% |
| 选错块 | 精确率、召回都 < 0.3 | 约 21% 至 24% | 约 20% | 约 12% 至 16% |
| 输出为空或零重叠 | 精确率、召回都为 0 | 15%（html）/ 2%（rs） | 11%（html）/ 4%（rs） | 28%（html）/ 16%（rs） |
| 少取 | 召回 < 0.3，精确率 ≥ 0.6 | 约 9% 至 11% | 2 页 | 约 10% 至 19% |

（括号为 html-extractor / rs-trafilatura 各自落入该类的页数。）
两者的失败高度重叠：在拉丁文字的 719 页里，两者落入同一类型的就有 202 + 96 + 45 页。**这是共同缺陷，不是各自的小毛病。**

### 抽样阅读得到的原因（按出现频率）

1. **多取：参考答案只是页面的核心，提取器取了整个主容器。** 商品页、软件下载页、小说目录页、个人博客、新闻页常见。
   参考答案是标题加正文开头（几百字），提取器连同规格表、配送说明、相关推荐、评论、版权声明一起取了（几千字，精确率 0.01 至 0.1）。
   **要注意：这部分有标注口径问题。** 对 LLM 使用场景来说，规格表和配送说明有时正是想要的内容。需要先定义产品对"主内容"的要求（见第 6 节）。
2. **选错块：核心很短或不是长段文字时，选中了页脚、版权声明、电话列表、导航。**
   例：新闻页只有两三句时选中了版权条款；企业站选中了分公司电话列表；论坛选中了页头。
   根因是"文本多、链接少"的启发式会把页脚当成正文。
3. **表格、列表、数据页：** 域名反查、球员数据、章节列表、租房图片页。内容短而结构化，提取器抓不到或抓成噪声。
4. **html-extractor 输出为空**（抽样 36 页里有 7 页，WCXB 开发集 28%）：没有 `<article>`、集合页、部分博客。
   rs-trafilatura 在同样页面上能给出东西（虽然不一定对）。**产品要求：不允许空输出，必须有兜底。**
5. **标注噪声（不是提取器的错）：** 至少 7 页的参考答案是另一种语言（英文页面配了中文参考答案，疑似机翻）；
   一页泰文页面的参考答案本身就是乱码。这些页面不应计入成绩，已在上面的数字里保留，影响小于 1%。
6. **编码在这个基准上无法评价：** WebMainBench 存的是已经解码的字符串，上面那个乱码页面说明解码错误发生在数据集生成时。
   要评价编码处理必须用原始字节，WCXB 的 `.html.gz` 是字节，可以用。

### 排除的猜想
- 我曾猜测 rs-trafilatura 会在中文字之间插入多余空格。统计后**没有区别**：每千个汉字中，参考答案 11.1 处、html-extractor 7.7 处、rs-trafilatura 7.2 处，不是差异点。

### 对算法优先级的含义
1. **精确率（多取）是头号问题，其次是选错块。** 两个提取器的召回约 0.89 至 0.90，精确率只有约 0.75 至 0.77。
   要解决的是"哪里是核心的边界"，而不是"把更多东西抓进来"。块级分类器（4.4 节）正对这个问题。
2. **核心锚点：** 用页面标题（`<title>`、`og:title`、`h1`）与某块文本的匹配、日期与作者行的位置，确定核心的起点，
   比"文本密度最大"更不容易选中页脚。
3. **同站模板学习：** 我们是爬虫，同一域名会反复抓到大量页面。比较同站点多页的 DOM 能直接找出导航、页脚、侧栏等重复模板，
   这是单页评测测不到、但线上最有价值的信号。需要另设评测（同站多页）。
4. **兜底：** 任何情况下不输出空；表格、列表页要有专门的输出路径（转成结构化列表，而不是丢弃）。
5. **分段输出而不是二分类：** 输出"核心 + 次要区块（规格、评论、相关）"，由调用方按需取舍，可同时满足"标注口径的主内容"与"LLM 想要完整信息"。

## 5.6 第一个块级分类器基线（`extract-eval blockclf`）

做法：把页面切成文本块（最近的块级祖先），约 100 个便宜特征（文本长度、链接占比、标点密度、标签与祖先标签、class 和 id 关键词、
位置、邻居块、各层祖先容器的文本占比、标题重合度，另一个模型还加上两个现成提取器对该块的覆盖率），用人工块标记做标签，
梯度提升树分类，输出被选中的块按文档顺序拼接的纯文本。**按域名切分**：训练 5,454 页，验证 779 页，测试 1,576 页，三者域名互不相交。
阈值在验证集上选，没有块被选中时退回概率最高的一块（不输出空）。

WebMainBench 保留的测试集（1,576 页），词袋 F1：

| 方法 | F1 | 对整页文本 | 对 html-extractor | 对 rs-trafilatura |
|---|---|---|---|---|
| 整页文本（不提取） | 0.663 | | | |
| html-extractor | 0.780 | | | |
| rs-trafilatura | 0.779 | | | |
| **块分类器（仅结构特征）** | **0.863** | +0.200 | +0.083 [+0.070, +0.096] | +0.084 [+0.073, +0.097] |

- 难度：困难 0.810 / 0.818（对 0.706 / 0.702），中等 0.878 / 0.874（对 0.784 / 0.789），简单 0.889 / 0.905（对 0.839 / 0.831）。
- 文字：拉丁 0.859 / 0.864（对 0.773 / 0.778，n=1,310），**中文 0.894 / 0.903（对 0.824 / 0.795，n=245）**。
  日语 3 页、韩语 5 页、俄语 9 页、阿拉伯语 2 页，样本太小，不下结论。

|---|---|

读法（要诚实）：
1. **域内（同一标注口径、不同域名）提升很大且稳**，置信区间不含 0。中文提升也在。
2. **跨数据集不成立：** 在 WCXB 上它只略好于 html-extractor，仍明显低于 rs-trafilatura（0.810 对 0.847）。
   说明模型相当程度上学到了 WebMainBench 的"核心"口径，没有学到通用的"主内容"。
   rs-trafilatura 的页面类型规则（论坛、商品等）是它在 WCXB 上占优的原因，我们的特征里没有页面类型，训练数据里也几乎没有这些页面类型的标签。
3. **加提取器特征有收益：** 域内 +0.006，跨数据集 +0.016。收益不大，但代价是每页多跑约 45 毫秒（两个提取器），是否值得要看后面的优化。
4. 预测本身每页约 0.8 毫秒；特征提取和解析的耗时我还没单独量。

下一步应对的方向：把 WCXB 的页面也变成块级训练数据（用它的参考文本去匹配块来打标签），混合两种口径训练，并加页面类型特征；
然后再用域名和数据集双重隔离的方式测泛化。

### 5.6.2 混合两种标注口径训练（`extract-eval mixed`）

做法：WCXB 没有块标注，所以用它的参考文本去匹配每个块（块的 3 词组被参考文本覆盖 ≥50% 记为正例）。先在 WebMainBench 上审计这个派生方法：与人工块标注的字符加权一致率 0.980，精确率 0.978，召回率 0.993；用派生标签重组文本的 oracle F1 为 0.957（人工标注 0.993），所以派生标签比人工标注略差，但可用。
划分：按注册域名哈希，两个数据集共用同一个函数，所以一个域名不会同时出现在一边的训练集和另一边的测试集。WebMainBench 训练/验证/测试 5,454/779/1,576 页，WCXB 1,344/204/460 页。WCXB 训练样本权重 ×3。新增“页面级特征”（URL 形状、结构化数据类型、文本在评论/商品/列表/表格块中的占比等，共 40 维，不需要页面类型标注）和可选的“标注口径标志”。阈值在各数据集自己的验证集上选。

| 模型 | WebMainBench 测试 F1 | WCXB 测试 F1 |
|---|---|---|
| 整页文本 | 0.663 | 0.688 |
| html-extractor | 0.780 | 0.794 |
| rs-trafilatura | 0.779 | 0.846 |
| 仅 WebMainBench 训练 | 0.863 | 0.815 |
| 仅 WCXB 训练 | 0.797 | 0.845 |
| 混合 | 0.848 | 0.836 |
| 混合 + 页面特征 | 0.854 | 0.838 |
| 混合 + 页面特征，不用提取器特征 | 0.857 | 0.822 |
| 混合 + 页面特征 + 口径标志 | **0.860** | **0.841** |

配对差（95% bootstrap CI）：混合+页面特征+口径标志 − rs-trafilatura：WebMainBench +0.081 [+0.071, +0.092]，WCXB −0.005 [−0.022, +0.013]；− 仅 WebMainBench 训练：WebMainBench −0.003 [−0.007, +0.003]，WCXB +0.026 [+0.015, +0.038]。

读法：
- 带口径标志的混合模型在两边都接近各自最好的单数据集模型：WebMainBench 与单数据集模型无显著差，WCXB 上与 rs-trafilatura 无显著差（置信区间跨 0），WebMainBench 上高出 0.08。没有出现“两边都妥协”。
- 口径标志有用且可控：同一模型把标志强制成另一种口径，在对应数据集上下降 0.02 到 0.04（0.860→0.817，0.841→0.825），说明模型确实学到了“核心”和“扩展”两种范围。这和输出契约“核心加区块”一致。
- 页面特征的增益小（+0.002 到 +0.006），在 WCXB 的列表页上较大（0.660→0.681，加口径标志后 0.745），其他类型没有稳定提升；论坛页仍落后 rs-trafilatura（0.629 对 0.738），商品页也落后（0.663 对 0.710），这是下一步要补的。
- 提取器特征在 WCXB 上仍有帮助（去掉后 0.838→0.822），在 WebMainBench 上不需要。
- 中文：混合+口径标志 0.892，与仅 WebMainBench 训练相同，html-extractor 0.824，rs-trafilatura 0.795。
- 局限：rs-trafilatura 的分类器和规则是在 WCXB 上调的，所以它在 WCXB 上的数字偏乐观；WCXB 各页面类型样本只有 28 到 232 页，类型级差异的置信区间很宽；论坛、商品、列表只有 28 到 33 页，不要过度解读。口径标志的阈值是在目标数据集验证集上选的。

### 5.6.3 各阶段耗时与块级新特征（`extract-eval timing`，`mixed` 第二版）

单线程、WCXB 300 页：分块 7.1 ms（p95 14.1），页面特征 2.7 ms，html-extractor 4.5 ms，rs-trafilatura 24.5 ms（p95 52.1）。模型预测另计，约 1 ms/页。所以完整模型约 40 ms/页，不用提取器约 11 ms/页；rs-trafilatura 占了完整路径的六成以上。
新增 6 个块级特征（含价格、含时间戳、含购买按钮词、含论坛词、前后块是否带时间戳）后：

| 模型 | WebMainBench 测试 | WCXB 测试 |
|---|---|---|
| rs-trafilatura | 0.779 | 0.846 |
| 完整（两个提取器 + 页面特征 + 口径标志） | 0.860 | 0.845 |
| 只用 html-extractor | 0.862 | 0.822 |
| 不用提取器 | **0.866** | 0.831 |

- 完整模型 − rs-trafilatura：WebMainBench +0.081 [+0.071, +0.092]，WCXB −0.001 [−0.016, +0.017]。
- WCXB 商品页 0.663→0.705，论坛页 0.629→0.640（仍低于 rs-trafilatura 的 0.738；论坛只有 33 页，商品 29 页，结论不稳）。
- 只用 html-extractor 在 WCXB 上显著低于 rs-trafilatura（−0.024 [−0.043, −0.003]），所以没有“便宜的一半”这个折中；要么完整，要么不用提取器。
- 取舍：不用提取器的模型在 WebMainBench 上最好，在 WCXB 上比完整模型低 0.014，但推理省约 29 ms/页，也不依赖第三方提取器。决定：`seesea-extract` 第一版内置“不用提取器”的模型，完整模型作为后续可选特性。

### 5.6.4 `seesea-extract` 第一版（`seesea-core/crates/seesea-extract`）

特征、分块、模型推理和 Markdown 渲染只在这个 crate 里有一份，评测框架直接依赖它，所以评测的就是发布的路径。内置模型是“不用提取器 + 页面特征 + 口径标志”，深度 8、最多 300 棵树，gzip 后约 1 MB（深度 10 的版本 23 MB，gzip 后 3 MB，F1 高约 0.006，没有采用以免仓库膨胀）。

|---|---|---|---|---|---|
| WebMainBench（1,576 页） | Core | 0.859 | 0.849 | 0.4% | 0.82 |
| WCXB（460 页） | Extended | 0.824 | 0.815 | 2.4% | 0.84 |

- 口径标志有效：用错范围会掉 0.01 到 0.011。
- LCS F1 比词袋 F1 低约 0.01，说明选中块的顺序基本正确。
- 已知限制：`page_type` 恒为 `None`；`needs_render` 只是启发式（选中文本少于 150 字符，且页面可见文本少于 300 字符或带有 JS 应用标记）；表格逐单元格输出；图片丢弃；块内换行（`<br>`）不保留。

### 5.6.5 性能优化（`cargo run --release --example profile`）

方法：先对 300 个 WCXB 页面分阶段计时（本机是共享桌面环境，perf 无权限，所以用手动埋点；每阶段取 5 轮最小值），再逐项优化，每一步都用逐页输出哈希（核心文本、区块、置信度、needs_render）对比优化前，300 页全部一致，之后在 2,036 个留出页上复测，F1 与优化前完全相同（0.859 / 0.824 / 0.813 / 0.848）。

| 阶段 | 优化前 ms/页 | 优化后 ms/页 | 做了什么 |
|---|---|---|---|
| HTML 解析 | 2.7 | 2.7 | html5ever，无法再省；只解析一次，元数据和分块共用 |
| 元数据 | 0.45 | 0.06 | 一次扫描全部 `<meta>`，选择器只编译一次 |
| 分块和特征 | 5.5 | 2.5 | 自上而下一次遍历带下状态、带上子树文本量，替代每个文本节点向上走一遍祖先链；每个元素的祖先信号只算一次再按位或；字符类别统计从 6 遍合成 1 遍；节点哈希表改用轻量哈希 |
| 页面级特征 | 1.65 | 0.65 | 7 个标签计数合并成一次 `<` 扫描；其余只剩 ASCII 小写化 |
| 模型预测 | 约 1.3 | 约 1.1 | 直接按列构造矩阵，不再复制每个块的特征行 |
| **extract() 合计** | **11.5** | **7.2** | **−37%** |

在评测框架里（含 2,036 页留出集的真实页面分布）单线程 `extract()` 从 17.0 降到 9.7 ms/页。

并行：
- 单页只有约 7 ms，页内拆分的线程开销大于收益，所以并行的粒度选“一页一线程”；新增 `Extractor::extract_batch`（特性 `parallel`，默认开启，基于 rayon），结果保持输入顺序。
- 吞吐（300 页，best of 3，本机 32 个逻辑核且同时跑着桌面应用）：1 线程 137 页/秒，2 线程 266，4 线程 538，8 线程 1,026，16 线程 1,642；32 线程反而降到 728。到 16 线程前接近线性扩展；超过物理核数后变差，这台机器无法区分是超线程、内存分配器争用还是桌面负载，生产上请按物理核数配置线程池，并在目标机器上重测。
- 模型预测在块数 ≥ 2,000 的大页上才启用页内并行。
- 没有做的：解析仍是最大的单项（37%），想再降只能换解析器或做流式预过滤；分词仍为每个块分配 `String`，约 0.35 ms/页；这两项收益有限，暂不动。

## 6. 已决定与待决定

已决定：
1. **路线：** 自建 `seesea-extract`（c）。5.6.2/5.6.3 的数据支持：自带块级分类器在 WebMainBench 上高出 rs-trafilatura 约 0.08，在 WCXB 上无显著差。
2. **中文是一等公民**，评测集与字符级分词从第一天做。
3. **离线训练的梯度提升树进入主路径**：纯 Rust（forust-ml），模型随 crate 发布，推理约 1 ms/页。
4. **第一版不依赖第三方提取器**（见 5.6.3）。

待决定：
1. **新 crate 的许可证。** 当前沿用主项目的 AGPL-3.0-or-later；改成 Apache-2.0 或 MIT 能让它更容易被采用，但一旦发布就难以收回。
2. **完整模型（含 rs-trafilatura 特征）是否作为可选特性**，换 WCXB 上约 1.4 个点。
3. **WCXB 与 WebMainBench 的数据许可：** 只用于评测和训练，原始页面不进仓库；训练出的模型权重是否可发布，需要再确认。

## 7. 落地顺序

已完成：评测框架（WCXB、WebMainBench）、同台基线、失败分析、块级分类器、混合口径训练。
1. `seesea-extract` crate：分块、特征、模型推理、保序 Markdown、核心加区块输出、置信度与 needs_render。特征代码只有一份，评测框架直接依赖该 crate，保证评测的就是发布的路径。
2. 用 crate 自带路径在两个基准上复测，作为回归门禁。
3. 自建中文和多语言评测集（带区块标注），并行建设。
4. Lightpanda 渲染回退（由 needs_render 触发），量化渲染能补多少。
5. 完整模型可选特性、同站模板学习、区块种类分类。
