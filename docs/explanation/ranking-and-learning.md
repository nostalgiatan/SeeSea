# 排序与学习

这一页解释分数是怎么算出来的，两个模型各自负责什么，第一层怎么从使用中学习，以及哪些结论是测过的、哪些不是。整体流程见[搜索管线如何工作](pipeline.md)。

## 两层分数

第一层只看摘要，目的是挑出值得下载的页面。第二层看过正文，决定最终排序。最终分数由第一层和第二层按固定比例混合：

```
最终分数 = 0.2 × 第一层 + 0.7 × 相关度 + 0.1 × 正文质量
```

第一层分数先归一到最高分为 1。相关度和正文质量由第二层给出。

两个修正：

- 查询里的某个词正好是站点名（`tokio` 对 tokio.rs，`postgresql` 对 postgresql.org，或 docs.rs 的第一级路径），并且正文相关度至少 0.3、质量至少 0.5 时，加 0.08。依据是问某个项目时，项目自己的站点通常是好答案。
- 没有读到正文的页面，分数是“第一层的摘要级分数”再乘 0.45，所以它们排在读过且相关的页面后面。之前不乘这个系数时，一个没读过的页面最高能拿到 0.62，足以压过读过正文、相关度中等的官方文档。

## 相关度从哪里来

相关度是三种信号的叠加，有多少模型就用多少。

**词法。** BM25、查询词在正文里的覆盖，以及标题与正文的一致性。标题匹配很高而正文不支撑时，标题项为负。这一层始终存在，没有模型时就是全部。

**嵌入相似度（bge-m3）。** 把查询和页面的若干段落变成向量，比较余弦相似度。每页取开头一段加上最匹配的几段，最佳段落起主要作用，第二好的段落加一点。余弦值按区间映射到 0 到 1，默认区间 0.3 到 0.75，是按 bge-m3 调的。嵌入分数占内容相关度的 0.8，但会乘以标题被正文支撑的程度，所以标题党页面无法靠语义相似度蒙混过关。

**交叉编码器（bge-reranker-v2-m3）。** 把查询和段落放在一起读。它能区分“谈到这个话题”和“回答了这个问题”，这是只比较向量做不到的。输出的 logit 经 `sigmoid((logit - center) / scale)` 映射成相关度，默认 `center = -4`、`scale = 3`：这个模型很严格，真正的答案也常常落在 -4 附近。它占内容相关度的 0.5，和下层分数（嵌入或词法）混合。

三种打分都要乘以页面内容的非重复度，也就是不同词三元组占的比例。把查询重复几十遍的页面，在三种打分里都会像完美匹配，乘上这个系数后趋近于 0。

## 章节选择

一个页面放不下字符预算时，先用词法挑出最有希望的 12 个片段，再交给已加载的模型（有交叉编码器就用它，否则用嵌入）重新打分，词法占 0.3，语义占 0.7。这样一个答案章节即使和查询没有共同词也能被选中。`--lexical-sections` 可以关闭这一步。

## 第一层怎么学习

读过正文之后，第二层给出的相关度（权重 0.7）和正文质量（0.3）会记到该页面的主机和返回它的来源名下；取不到正文的记 0.15。观察值按 90 天的半衰期指数衰减，向全局均值收缩，至少约 3 次观察才生效。生效后给第一层加一个有界的修正：主机最多约 ±0.075，来源最多约 ±0.025，在 `score_parts.learned` 里可见。`seesea feedback good|bad` 相当于 5 次观察。

学习有一个明显的偏差：只有被读取的候选才有观察。为了缓解，`explore` 设置每次搜索以一定概率改读一个排名靠后的结果。

学到的内容保存在数据目录的 `learn.json`，服务进程每 30 秒写盘一次。

## 结果的多样性

同一个主机的结果从第三个起，每多一个分数乘 0.88，免得一个站点占满整页。标题相近且来自不同站点的结果并成同一个事件，主结果每多一个独立站点加 0.03 分，最多 0.09，因为被多家独立报道本身是证据。

## 测过什么，没测什么

在 `tools/search-eval` 的 8 个查询上，`deep` 模式的 nDCG@5：

| 配置 | nDCG@5 |
|---|---|
| 仅词法 | 0.828 |
| bge-m3 嵌入 | 0.952 |
| 仅交叉编码器 | 0.945 |
| 嵌入加交叉编码器 | 0.970 |

这个集合只有 8 个查询，而且已经接近饱和，差异不应过度解读。

没有测过的：

- 第一层的学习是否提高了 nDCG。8 个查询的集合不足以证明。
- 站点名加分和未读页面降权对真实查询的影响。它们是针对一次与 Tavily 的对比里看到的现象加的，那次试验只有 4 条查询。
- 语义映射区间对 bge-m3 以外的模型是否合适。

速度方面，在一块 RTX 5070 笔记本 GPU 上，交叉编码器稳定状态下每个约 280 词元的查询加段落对需要约 70 毫秒，批量并不会更快，耗时随数量线性增长。第一次调用有额外的预热开销。
